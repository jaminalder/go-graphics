Lesson 01 / 8 minutes

One request.
Two kinds of work.

Your win: trace a generated image across the process boundaries, and explain why a renderer outage need not take the gallery down.

Connects: HTTP → application queue → Unix socket → child process → image cache

First, make a prediction

A visitor opens the gallery. Another asks for four new images. Which parts of the system do both requests need, and which parts does only the second need?

The HTTP handler validates the request and asks the application to admit work. Expensive rendering runs in a separate child process. One queue in web owns the budget; the renderer supervisor accepts one active job and starts its own executable with --child.

Follow the boundary

Highlighted = involved in this scenario

Browse → Caddy → web → browser

Caddy forwards to web:8080. Web serves server-rendered HTML and embedded catalogue assets. Existing cached image requests also terminate at web. The renderer does no work for a gallery view.

Admit → execute → publish

Web admits a validated recipe to the bounded queue. It calls the renderer over /run/art/renderer.sock. The supervisor starts a child with a deadline and output limit. PNG bytes return to web, which publishes them into its cache; the browser retrieves the result through Caddy.

A failed render path, a live gallery

The stopped renderer cannot answer compatibility probes or execute work. artctl ready fails; artctl live can still succeed. The gallery survives. This illustrates intended isolation; real OOM behaviour still needs a target-host drill.

Three details make the diagram true

Only the edge is published

Caddy owns the host port mappings. Web lives on the internal proxy network; renderer uses network_mode: none. Caddy has another network for external access.

A socket is a different path

Both services mount the socket volume. Web has a read-only mount and group permission to connect to the socket. That does not make socket communication read-only.

Resources belong to groups

Web has 384 MiB and 0.5 CPU; renderer has 2 GiB and 1.5 CPU including its child. These configured limits must be inspected and exercised on the actual host.

Source: Compose services, mounts and limits; supervisor and socket protocol. Background: Docker’s network model.

You stop only renderer. What should still work?
Answer key · open after predicting

Gallery pages remain available. Web still serves HTTP and embedded assets; existing cached downloads can remain available too. Renderer readiness fails because compatible generation is unavailable.

Inspect the real wiring

Run from the repository root. The first command resolves the configuration without starting containers. For the remaining commands, start the existing local rehearsal if it is not already running.

docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml config
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml ps
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml exec -T web /app/artctl live
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml exec -T web /app/artctl ready

Look for: three services; Caddy’s loopback mappings; no web published port; renderer’s disabled network. With a healthy local stack, both probes should exit successfully. If readiness fails, inspect renderer health and logs before drawing a conclusion.

Optional failure drill · local art-local project only

Before stopping anything, save any local exploration you care about. This interrupts rendering. Predict the gallery and probe results, then use the same Compose project for recovery.

docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml stop renderer
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml exec -T web /app/artctl live
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml exec -T web /app/artctl ready
# ready is expected to fail while renderer is stopped.
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml up -d --no-build --wait renderer
docker compose -p art-local --env-file deploy/local.env -f deploy/compose.yaml exec -T web /app/artctl ready

Between stop and recovery, open http://localhost:8088. Record the page behaviour and the probes’ exit results. If recovery fails, inspect logs --tail 100 renderer with the same prefix. The isolated automated alternative is make check-compose.
