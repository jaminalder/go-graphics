First separate a new host from a new release

INFREQUENT / HOST LIFECYCLE

Provision and prepare

Terraform owns cloud objects and their state mapping. Cloud-init sets up the OS; the bootstrap script installs the container runtime. State locking, firewall, console recovery and backup access need proof before relying on this host.

Host and state runbook ↗

REPEATED / RELEASE LIFECYCLE

Upload and activate

The operator uploads a retained release to /opt/art/releases/<commit>. The host activation script reads environment and approval files in /etc/art, then runs Compose with exact image IDs.

Release runbook ↗

A source change does not require a Terraform apply. A cloud-init change can require host replacement, which is a different operation. Terraform state maps managed cloud objects; it does not contain the web process’s in-memory queue.

Choose a failure point

A teaching simulation; no server commands run

One queue across replacement

After smoke passes, stop accepting new jobs and confirm the old queue is empty. Stop old web and renderer, switch /opt/art/current, recreate services and check them. There is a brief restart and in-memory explorations are lost. Caddy may also be recreated if its image changed.

Fail before disturbing the current release

Smoke validates Caddy and runs private web/renderer probes in a separate project with generation off. Failure exits before changing the old release. Temporary smoke volumes are cleaned up; the live project’s volumes are separate.

Fail before replacement

A missing metric or drain timeout aborts activation. The recovery handler attempts to reopen generation on the old release. The operator must verify the result. Treat an incident kill switch separately: this recovery path tries to enable admission.

Fail after replacement started

The handler attempts to stop the candidate, point current back to the previous release, recreate its services and check renderer readiness. If this was the first installation, it removes candidate containers and the current pointer while preserving volumes. Check the exit status and logs; recovery can itself fail.

The private candidate smoke fails. What happens to the current release?
Answer key · open after predicting

It keeps running unchanged. smoke-release.sh runs before the activation script changes admission or the current pointer. Its temporary project is isolated and generation is disabled. Later failures follow different recovery paths.

What survives replacement?

A healthy previous image does not bring back vanished memory. Volumes live outside the container’s image, but surviving container recreation does not make a volume an independent backup. Docker’s volume lifecycle is the underlying contract.

StateContainer replacementWhole-host loss
Workspaces, favourites, jobs in web memoryLost when web exits. Draining only waits for queued/running jobs.No durable-session recovery promise.
Image cache / socket volumeNamed volumes survive ordinary recreation. Cache is disposable; socket is runtime IPC.Recreate; not the authoritative artwork recipe archive.
Caddy data / config volumesRetained for account, certificates and configuration state.Restore independent backup with ownership intact.
Images / release files / operator configKept outside running processes; retain the previous working release.Restore retained archives and /etc/art from independent storage.
Terraform state and accessUnaffected by application recreation.Recover from the independent backend and operator credentials.

Application cache and favourites have separate semantics. See the recovery contract; a proposed two-hour restoration goal has not yet been measured.

Rehearse the decision without a server

Read activate-release.sh. Find where changed=yes is set, then find the two branches in rollback(). Place the four scenarios above on either side of that boundary.

To exercise the script’s existing mocked failure-path tests locally, run from the repository root:

python3 deploy/tests/test_activation.py

Expected evidence: seven tests pass. These simulate deployment commands and assert the activation decisions; they do not prove real host recovery, public TLS, or renderer OOM behaviour.

On an approved host later: inspect the active release

These are host inspection commands for a deployed release, not commands to run on your laptop. The release wrapper selects the fixed project, operator environment and recorded image IDs.

readlink -e /opt/art/current
sudo /opt/art/current/deploy/scripts/compose-release.sh /opt/art/current ps
sudo /opt/art/current/deploy/scripts/compose-release.sh /opt/art/current exec -T web /app/artctl ready

Activation itself is an operator action documented in the runbook. Use the full retained commit ID; verify recovery after any nonzero exit.

The next work is evidence

Move into the local boundary lab, then remote state, host bootstrap, staged HTTPS and a measured restore. The launch checklist holds the target-host and publication gates. A passing simulation is a good rehearsal; record real commands, output, environment and elapsed time when operating the system.
