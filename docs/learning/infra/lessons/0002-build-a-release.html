The image count is not the process count

deploy/Dockerfile compiles four commands once for the application image. Compose uses that image for both web and renderer, choosing a different entrypoint and user for the latter. Caddy comes from a separate edge image. Two packaged filesystems support three service roles.

Source: Dockerfile and build-release.sh. Docker’s multi-stage build contract explains why copying outputs leaves the build tools behind.

What happens after a push?

CI is automated verification of a revision. The checked-in GitHub Actions workflow runs on pushes and pull requests. It builds a release as part of verification; it has no upload or host activation step.

  1. Check Go: make check, targeted race tests and vulnerability scanning.
  2. Check the browser: install test-only Node dependencies and Chromium; exercise the actual journeys.
  3. Check packaging and changes: cross-build a Linux amd64 release, run activation failure-path tests and shell syntax checks.
  4. Check infrastructure: Terraform formatting, initialization with -backend=false, and validation.
  5. Check the runtime: run the isolated Compose test against real rendering and service boundaries.

A green workflow has a precise meaning

It is evidence about that revision under the tested conditions. It does not upload the archive, buy a server, change DNS, prove live TLS or activate production. The workflow does not retain the built archive with an artifact-upload step, either; an operator builds and retains a release for delivery.

Read the actual workflow. Node and Playwright belong to verification; they are absent from the scratch application image.

Which file tells activation the exact two images to run?
Answer key · open after predicting

Read images.env. The builder records exact sha256 image IDs for app and edge, plus the source revision. Activation loads the checked archive and uses those IDs; a branch name or moving tag is insufficient.

Inspect a release, or follow its construction

From the repository root, first look for an already retained release. If no release is present, inspect build-release.sh; an absent directory is not a broken app. Building a new release needs Docker, image downloads and a clean committed checkout.

ls out/releases/
# For a retained release, replace FULL_COMMIT with its directory name.
cat out/releases/FULL_COMMIT/images.env
cat out/releases/FULL_COMMIT/manifest.txt
# Run checksum verification inside that release directory:
cd out/releases/FULL_COMMIT
shasum -a 256 -c SHA256SUMS

Find three identities: the source commit, the app image ID and the edge image ID. Then find one deployment file covered by SHA256SUMS. A checksum detects changed bytes; trust in those bytes still comes from the operator’s delivery channel.

Compare three kinds of identity

Source revision: identifies the committed code. Image ID: identifies the local Docker image configuration and its referenced filesystem layers. Archive checksum: verifies a file’s bytes. Our script uses image IDs and an archive checksum; it does not pretend a tag is immutable or that a checksum authenticates an unknown sender.
